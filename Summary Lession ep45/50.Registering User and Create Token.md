## Auth (Registering Users)

### 1. API Routs (routes/api.php)

```php
Route::post('/register', [\App\Http\Controllers\Api\AuthController::class,'Register']);
```

### Create Auth Controller

```php

class AuthController extends Controller
{
    public function Register(Request $request)
    {
        $request->validate([
            'name' => 'required|string|max:255',
            'email' => 'required|email|max:255|unique:users',
            'password' => 'required|min:8|confirmed',
        ]);

        $user = User::create([
            'name' => $request->name,
            'email' => $request->email,
            'password' => Hash::make($request->password),
        ]);

        // Create a new token for the user
        $token = $user->createToken('auth_token')->plainTextToken;

        return response()->json([
            'message' => 'User registered successfully',
            'access_token' => $token,
            'token_type' => 'Bearer',
            'user' => $user,
        ], 201);
    }
}
```

## Learn Contex

### 1. What problem Sanctum solves (context First)

In API-based apps:

- There is no session
- There is no cookie (usually)
- Every request must prove who the user is

=> So the question is:

> " How does the server know who is calling this endpoint?"

### 2. What exactly is a Sanctum token?

When you call:

```php
$token = $user->createToken('api-token')->plainTextToken;
```

Laravel does three important things:

#### 1. Generate a long random string

---

Something like

```plaintext
1|brWdDDbvNsQOGtTgOjdWilc0hTsiWi7znKo3cltJ1ebfeada
```

**this is the plaintext token :**
you can see this only ONCE.

#### 2. Hashes the token before storing it

---

This is store in database table name `personal_access_token` table:

| Column          | Value             |
| --------------- | ----------------- |
| token           | hashed_value_here |
| tokenable_id    | user_id           |
| tookenable_type | App\Models\User   |

### 🔐 Security reason:

> If DB leaks -> attackers can'ts user tokens

It's same idea to `hashed_password`

So:

#### `The token in DB ≠ token sent to client`

#### 3. Returns the plain token to the client

This is what your API returns:

```json
{
    "token": "1|brWdDDbvNsQOGtTgOjdWilc0hTsiWi7znKo3cltJ1ebfeada"
}
```

📌 **Important Point**

> Laravel will never show this token again.

---

### 3. What the client does with the token?

- The client (Postman/ Mobile app/ Frontend):
- Stores the token (localStorage, memory, secure storage)
- Sends it with every request

### Header Format:

Autorization: `Bearer 1|brWdDDbvNsQOGtTgOjdWilc0hTsiWi7znKo3cltJ1ebfeada`

**=> This header is the proof of indentity.**

### 4. what happpens on every protected request?

**Example:**

GET /api/posts

Autorization: `Bearer 1|brWdDDbvNsQOGtTgOjdWilc0hTsiWi7znKo3cltJ1ebfeada`

### Laravel Does This in Internally:

1. Reads the Authorization header
2. Extracts the token
3. Hashed it
4. Looks it up in `personal_access_tokkens` table
5. Finds the related user
6. Sets:

```php
auth()->user();
$request->user();
```

If no token or invalid token -> ❌ 401 Unauthorized.

### 5. Where `auth:sanctum` fits in ?

```php
Route::middleware('auth:sanctum')->group(function(){

})
```

### This middleware says:

> " Do not allow this route unless a valid Sanctum token exists."

- No token -> blocked
- Invalid token -> blocked
- Valid token -> allowed ✅

### 6. Why return token on register?

#### Real-World reasoning:

- Mobile apps -> auto-login after register
- SPAs -> no extra login step
- Better UX

Some systems don't - both are valid, but returnin gtoken is common

### 7. One-sentence Summary:

> " Sanctum authenticates API users by issuing a token, hashing it in the database, and validating it on every request via the Autorization header."
