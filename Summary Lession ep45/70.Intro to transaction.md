## What are Database Transactions ? (Concept First)

A transaction is a way to group multiple database operations so they behave as one single unit of work.

**_That means:_**

- Either all operations succeed.
- Or non of thme are applied
- There is no half-finished state.

### Real-life analogy

**Think of a bank transfer:**

- Withdraw money from Account A
- Deposit money into Account B

If withdrawal succeds but deposit fails -> problem
Transactions prevent this situation.

### Why Transactions Matter in Real Laravel Projects

In real applications (eCommerce, APIs, CMS, B2B system), you often:

- Create records
- Update related tables
- Reduce stock =1
- Log actions
- Send notifications

If any step fails, the database must return to its previous clean state.

Without transactions -> data corruption ❌
With transactions -> data consistency ✅

### ACID Principles (Short & Important)

Transactions follow ACID:

- A - Atomicity: All or nothing
- C - Consistency: Database remains valid
- I - Isolation: Transactions don't interfere
- D​​​ - Durability: Once committed, data stays saved

You don't usually code ACID directly - Laravel + DB handle it, but we must understand it as an advanced developer.

### Transactiom in Laravel (Core Usage)

Laravel provides transactions via the DB facade.

**_Basic Syntax:_**

```php
DB::beginTransaction();
User::create([
    "name" => "Ra Vattra",
    "email" => "ravattrasmartboy@gmail.com",
    "password" => bcrypt("webcoding@gmail.com"),
])

$user = User::find(1);

if(!$user){
    DB::rollBack();
}

$user->update(['name'=>'updated']);
DB::commit();

```

**Example with try and catch**

```php
try{
    $user=User::create([
        'name' => 'Ra Vattra',
        'email' => 'ravattrasmartboy3@gmail.com',
        'password' => bcrypt('secret123'),
    ]);
    if(!$user){
        throw new \Exception('User creation failed');
    }

    $user->update([
        'name' => 'Updated Name'
    ]);

    DB::commit();
} catch(\Throwable $e){
    DB::rollBack();
    throw $e;
}
```

### When we should use TRANSACTIONs?

Use transactions when:

- Multiple related dB operations
- Financial operations
- Inventory management
- User + Profile creation
- Any business-critical logic

Do NOT use transactions for:

- Simple single queries
- Read-only oerations
